Debugging Pod egress, inside out

1

DNS

kubectl exec -it app -- nslookup api.example.com

2

Connectivity

kubectl exec -it app -- curl -sv https://api.example.com

3

NetworkPolicy

kubectl get networkpolicy -n app # default-deny? DNS allowed?

4

Node

kubectl debug node/<node> -it --image=busybox

5

Cloud network

Route 0.0.0.0/0 → NAT · SG / NACL / NSG egress · firewall logs

6

Proxy

Corporate proxy? Check HTTP_PROXY / NO_PROXY in the Pod

Model answer: “I go from the inside out, one layer at a time. First DNS: can the Pod resolve the name? If not, it’s CoreDNS or a NetworkPolicy blocking port 53. Then connectivity with curl -v, to see whether it’s a timeout — network — or a TLS or HTTP error — application. Then NetworkPolicies in the namespace. Then I check whether the node itself can reach out with kubectl debug node; if the node can’t either, it’s the cloud network: the route table, the NAT Gateway, Security Groups, NACLs or the NSG, and the firewall logs. Finally, in corporate environments, the proxy variables.” ES: Timeout = red (ruta/NAT/firewall). "Connection refused" o error TLS = sí llegó, el problema está del otro lado. Esa distinción suena muy senior.
