Liveness vs readiness probe

Terraform state

remote backend + locking

State in S3, Azure Blob or GCS with locking; plan on every PR; drift found with terraform plan

CrashLoopBackOff: “The container starts and dies over and over, and Kubernetes backs off between restarts. I run kubectl describe pod for the last state and exit code — 137 means OOMKilled, so I look at memory limits —, then kubectl logs --previous to see why the previous container died, then events. Common causes: a bad config or missing Secret, a failing liveness probe, or the app crashing on startup.” Liveness vs readiness: “Liveness answers ‘is it alive?’ — if it fails, the kubelet restarts the container. Readiness answers ‘can it receive traffic?’ — if it fails, the Pod is removed from the Service endpoints but not restarted. There’s also a startup probe for slow-starting apps.” Terraform state: “The state maps the code to real resources. In a team it lives in a remote backend — S3 with locking, Azure Blob or GCS — so two applies can’t run at once. We run plan on every pull request and apply after review.” ES: Estas no estaban en el correo del reclutador, pero son las repreguntas más probables a partir de tus respuestas.
