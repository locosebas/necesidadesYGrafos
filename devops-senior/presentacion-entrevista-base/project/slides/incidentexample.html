Use this as a worked example if they ask “tell me how you would handle…”. Say it in order: “At 14:02 an SLO burn-rate alert fires: 12% of 5xx errors on the checkout API. I acknowledge it, confirm it on the dashboard and declare a SEV2. The first question is: what changed? There was a deploy at 13:58, so I don’t start debugging — I roll back first, with kubectl rollout undo or by syncing the previous revision in Argo CD. By 14:12 the error rate is back to baseline and I update stakeholders. Then, with the service stable, we find the root cause — say, the new version exhausted the database connection pool — and in the postmortem we add automated canary analysis on the error rate and an alert on pool saturation, so the next bad deploy is stopped at 5% of the traffic.” ES: Esto es un escenario ilustrativo, no un incidente real tuyo.
