1 · E-commerce en AWS

El payment service se cae y arrastra a todos

  • Cascading failure (efecto dominó): HTTP síncrono sin timeouts, retry storms, recursos compartidos sin límites
  • Timeouts en todas las llamadas · retries con exponential backoff + jitter
  • Circuit breaker, 3 estados: closed (llama) · open (falla rápido) · half-open (prueba unas pocas)
  • Bulkhead: requests/limits, node group dedicado, pool de conexiones propio, PDB, anti-affinity entre AZ
  • Liveness solo revisa el proceso; readiness saca el pod del balanceador
Guion: There are two problems: why payment crashes, and why it takes everything else down. The cascade happens because calls are synchronous with no timeouts, retries pile up, and resources are shared. To stop the domino effect: timeouts everywhere, retries with exponential backoff and jitter, a circuit breaker, which is closed while payment is healthy, opens after repeated failures to fail fast, and goes half-open to test recovery. And bulkheads, so payment has its own resources and can't starve the rest of the site.
1 · E-commerce en AWS

La compra asíncrona con cola

  • Orden PENDING → cola (SQS, Amazon MQ, MSK/Kafka) → payment workers → PAID / FAILED
  • Idempotency key: nunca cobrar dos veces aunque el mensaje llegue repetido
  • DLQ (Dead Letter Queue) para los mensajes que fallan N veces
  • Saga pattern: acciones de compensación si un paso falla
  • Prevención: chaos engineering (AWS FIS, Chaos Mesh), canary con Argo Rollouts, SLO de checkout
Guion: Long term, I'd move payments to an asynchronous flow. The web service creates the order as pending and puts a message on a queue, like SQS or Kafka. Payment workers consume it, call the gateway with an idempotency key so we never charge twice, and mark the order as paid or failed. Messages that keep failing go to a dead letter queue, and a saga with compensating actions handles partial failures. That way a payment problem never takes down the whole website.

2 · Terraform en producción

State lock huérfano: 7 pasos antes de force-unlock

  • El lock no es el problema, nos protege; el riesgo real es un state que no coincide con AWS
  • 1 congelar · 2 ¿el proceso sigue vivo? (SIGINT, no matar) · 3 backup: terraform state pull, errored.tfstate
  • 4 ¿qué cambió? CloudTrail + plan guardado · 5 force-unlock solo si todo se cumple
  • 6 reconciliar: plan -refresh-only, import blocks · 7 reanudar por CI + postmortem
  • Prevención: timeout del job mayor que el apply más largo y SIGINT con periodo de gracia
Guion: The lock isn't the problem, it's protecting us. The real risk is a state file that no longer matches AWS. So before any force-unlock I freeze changes, confirm the process is really dead, back up the state and look for an errored.tfstate, and use CloudTrail to see what actually changed. Only then do I force-unlock, reconcile with a refresh-only plan and import blocks, and resume through CI. To prevent it, the CI timeout must be longer than the longest apply, and CI should send SIGINT so Terraform can write the state and release the lock by itself.
2 · Terraform en producción

Drift por un CIDR agregado a mano en un incidente

  • No lifecycle { ignore_changes } amplio: deja un punto ciego permanente en un security group
  • No apply normal: borraría 10.55.8.0/24 y volvería el outage
  • Verificar: CloudTrail (quién, qué puertos), VPC Flow Logs, de quién es el CIDR, causa raíz
  • Codificar la regla en Terraform con ticket → plan limpio · add before remove si se angosta
  • Guardrails: drift detection nocturno (plan -detailed-exitcode), AWS Config / EventBridge, CODEOWNERS
Guion: I'd neither ignore the drift nor blindly revert it. A broad ignore_changes turns the security group into a permanent blind spot, and a normal apply would remove the rule and bring the outage back. So I verify what the emergency rule really opened and who needs it, using CloudTrail and VPC Flow Logs, codify the right version in Terraform until the plan is clean, and add nightly drift detection and alerts on manual changes, so emergency fixes become code within a day.

4 · Canary con GitOps

Las 4 acciones de los primeros 10 minutos

  • 1 · Abortar el canary con el controlador: kubectl argo rollouts abort → 100 % al stable, sin drift con Argo CD
  • 2 · Vigilar métricas y trazas del servicio y de la dependencia; comparar llamadas, retries y timeouts canary vs stable
  • 3 · Verificar el digest real de cada cohorte (imageID en los pods) contra el historial del tag en ECR
  • 4 · Git igual a la decisión: revert del PR de promoción, imagen fijada por digest (image@sha256:...)
  • Seguimiento: ECR tag immutability y digests en todos los overlays de producción
Guion: First, I abort the canary with the rollout controller, which sends all traffic back to stable and changes the rollout status, not the spec, so Argo CD's auto-sync doesn't fight it. Third, I check the actual image digest running in each cohort, because the tag was overwritten. Fourth, I make Git match the decision: revert the promotion and pin the last known-good image by digest, then enable tag immutability in ECR.

Video · Rollout fallido con migración de base de datos

  • Pausar el rollback: versión vieja + esquema nuevo = segundo outage
  • 3 preguntas: ¿migración aditiva o destructiva? ¿terminó completa? ¿ya hay datos nuevos en el formato nuevo?

  • Antes de todo: confirmar un snapshot reciente de la base de datos
  • Para evitarlo: expand-contract (parallel change)
Guion: First, let's pause the rollback: the old version may not work with the new schema, and we could cause a second outage. I need three answers: was the migration additive or destructive, did it fully complete, and has new data already been written in the new format? If it's backward-compatible, we roll back the app. If not, we roll forward with a fix, because undoing the migration could lose data. Either way, I confirm we have a recent snapshot first. To avoid this in the future, we use expand-contract: add first, migrate the code, and remove the old columns in a later release.
5 · platformctl

Bloque 5 · platformctl v1: los 4 riesgos

  • 1 · Secretos en los logs: log.info(dict(os.environ)) deja ver AWS_SECRET_ACCESS_KEY, tokens de CI
  • 2 · Clúster equivocado: substring (prod también es preprod), sin paginación, None silencioso, ENV=prod por defecto
  • 3 · Command injection: subprocess.run(..., shell=True) con f-strings + grep sobre texto
  • 4 · Falla en silencio: no revisa return codes, sin timeouts, siempre imprime "done", selector vacío, sin dry-run
Guion: The four production risks are: first, it logs the entire environment, so AWS keys and CI tokens leak into logs. Second, it can target the wrong cluster: it matches by substring, so prod also matches preprod, it ignores pagination, and it defaults to production. Third, shell=True with f-strings allows command injection. And fourth, it fails silently: no return-code checks, no timeouts, an empty selector, and it always prints done, so during an incident the engineer believes the mitigation worked when nothing happened.
5 · platformctl

Diseño de platformctl v2

  • 2 subcomandos: rollout status (solo lectura) y pods restart con --env --namespace --deployment --reason, sin defaults peligrosos
  • Targeting seguro: config versionada env → clúster exacto, sts get-caller-identity, --context en cada llamada
  • Dry-run por defecto; --execute + escribir el nombre del entorno para confirmar en producción
  • Eviction API + PodDisruptionBudgets, lotes pequeños, máximo por corrida, RBAC mínimo, sin drift con Argo CD
  • Exit codes documentados (0 éxito · 1 falló · 2 input · 3 guardrail · 4 parcial · 5 timeout/auth), --output json, stdout vs stderr
Guion: Version two has two subcommands with required inputs and no dangerous defaults. It resolves the environment to an exact cluster and account from a versioned config, verifies the caller identity, and never changes the global kubeconfig. It's dry-run by default and shows exactly which pods it would restart. When it executes, it uses the Eviction API, so it respects PodDisruptionBudgets, in small batches, waiting for pods to be ready. And it ends with one clear success or failure line, documented exit codes and JSON output, so both humans and CI can trust the result.
