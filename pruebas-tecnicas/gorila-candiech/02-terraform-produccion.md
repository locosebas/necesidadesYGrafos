# Bloque 2 - SaaS en EKS gestionado con Terraform

**Escenario (resumen):** on-call Senior Platform/DevOps en un SaaS sobre AWS. EKS en una región;
VPC, subredes, security groups, IAM y node groups en Terraform con state remoto compartido. Los
applies los hace CI tras revisión, con un proceso break-glass para emergencias.

---

## Pregunta 1 - Revisar un `terraform plan` contra producción (approve / block / split-rework)

Plan: `6 to add, 4 to change, 2 to destroy`, con: `-/+ aws_iam_role.eks_nodes` (forces replacement, address changed), `~ aws_eks_node_group.gpu` launch template 12 → 13, `- aws_subnet.private["us-east-1b"]` / `+ ["use1-az2"]`, `- aws_security_group_rule.api_old` / `+ api_new`.

```text
DECISION: Split / rework. I would not apply this plan to production as-is.

Three of the four items (IAM role, subnet, security group rule) are code refactors that Terraform interprets as destroy + create, even though the real infrastructure is not supposed to change. They should become no-ops using "moved" blocks or "terraform state mv". The GPU launch template change is the only real change: it is legitimate, but it should ship in its own PR, in a controlled rollout window.

I would also flag an inconsistency: the summary says "2 to destroy", but the excerpt shows 3 destroy actions (IAM role replacement, subnet, security group rule), and only part of the 6 adds / 4 changes is visible. Before approving anything I would request the full plan generated by CI from the saved plan file (terraform show tfplan). I won't approve a production plan I can't fully see, and the mismatch may mean the excerpt is stale.

HIGHEST-RISK ITEM 1: -/+ module.eks.aws_iam_role.eks_nodes (replace)

Why it is risky:
- "forces replacement (address changed)" means the resource was moved/renamed in the code without a moved block. The role itself does not need to change (the name is identical), but Terraform will destroy and recreate it.
- IAM role names are unique, so the old role must be destroyed before the new one is created. During that window every EKS node loses its IAM identity: the kubelet can't authenticate (nodes go NotReady), the VPC CNI can't assign pod IPs, and nodes can't pull images from ECR. This is a cluster-wide outage risk for live customer traffic.
- Even with the same name, the recreated role gets a new unique role ID. Resource policies that reference the old role (KMS key policies, S3 bucket policies, cross-account trust policies) silently stop working. Since the ARN is "known after apply", the node groups and the aws-auth ConfigMap / EKS access entries that reference it may also be updated or replaced.

Evidence / change I would request:
- Add a moved block (or run terraform state mv through the controlled process) mapping the old address to module.eks.aws_iam_role.eks_nodes.
- Acceptance criterion: a new plan showing no changes for this role, and no node group or access-entry changes caused by it.
- Add lifecycle { prevent_destroy = true } on critical identity resources like this one.

HIGHEST-RISK ITEM 2: - module.network.aws_subnet.private["us-east-1b"] / + module.network.aws_subnet.private["use1-az2"]

Why it is risky:
- The for_each key changed from an AZ name (us-east-1b) to an AZ ID (use1-az2). Terraform sees two different resources, so it plans to destroy a production private subnet and create a new one.
- That subnet holds EKS nodes, pod ENIs, internal load balancers and possibly VPC endpoints. The likely outcomes are that AWS rejects the delete with DependencyViolation and the apply fails halfway, leaving production in a partial, inconsistent state; or, if dependencies are torn down, we lose an entire AZ's worth of capacity while the EKS cluster and node groups still reference the old subnet ID.
- The new subnet would likely reuse the same CIDR, causing a conflict.
- AZ names are mapped per account: us-east-1b in this account is not guaranteed to be use1-az2, so the "same" subnet might land in a different physical AZ and break the AZ balance of the node groups and of the GPU capacity.

Evidence / change I would request:
- Proof of the AZ name-to-ID mapping in this account: aws ec2 describe-availability-zones --region us-east-1 --query "AvailabilityZones[].[ZoneName,ZoneId]"
- If us-east-1b = use1-az2, migrate the state with a moved block from ["us-east-1b"] to ["use1-az2"]. Acceptance criterion: a new plan with 0 subnet changes.
- If the mapping does not match, this is a real network migration, not a refactor. It needs its own design (create the new subnet first, drain and migrate node groups, then decommission the old one), its own change request, and an owner from the networking team.

OTHER ITEMS (lower risk, but still not in this PR):
- Security group rule api_old -> api_new: also a rename. Terraform may delete the old rule before creating the new one, leaving a brief window with no API access, or fail with a duplicate rule error. Handle it with a moved block too.
- GPU node group launch template 12 -> 13: the only real change. Terraform shows it as "in-place", but EKS performs a rolling replacement of every GPU node. For latency-sensitive inference I would require a diff between versions 12 and 13 (AMI, user data, instance type), PodDisruptionBudgets and a conservative max_unavailable, confirmed GPU capacity, an off-peak window, latency monitoring, and a rollback plan (revert to version 12).

PROPOSED SEQUENCE:
1. PR A: state-only refactor with moved blocks. The plan must show 0 to add / 0 to change / 0 to destroy.
2. PR B: GPU launch template v13, applied by CI in a scheduled window.
3. Guardrail: policy-as-code in CI (OPA/Conftest, Checkov or Sentinel) that blocks production plans containing deletes or replacements of IAM roles, subnets or node groups without an explicit override.

Nothing here is an emergency, so there is no justification for break-glass or for rushing it.
```

## Pregunta 2 - Apply de CI se quedó en timeout y dejó el state lock (5–7 pasos antes de force-unlock)

```text
Principle: the lock is not the problem, it is protecting us. The real risk is a state file that no longer matches AWS. Force-unlocking first and investigating later can lead to a corrupted state or duplicated infrastructure.

1. Freeze all production changes. Announce in the team/incident channel that nobody runs apply, force-unlock or manual changes on prod until further notice. Pause the production CI pipeline so no queued job or retry grabs the lock the moment it is released. Assign one owner for the recovery.

2. Verify whether the lock holder is really dead. The lock belongs to ci-prod-apply@runner-17. Check the CI system and runner-17 itself: is the job still running, and is a terraform process still alive on the runner/pod? "Stopped logging" does not mean the process stopped; it could still be applying or waiting on a slow resource such as an EKS node group. If it is alive, do not unlock: let it finish, or stop it gracefully with SIGINT so Terraform completes in-flight operations, writes state and releases the lock itself. Also confirm the lock entry in the backend (the DynamoDB lock table for the S3 backend) matches Lock ID 4f7e0a7b-2b7b-4f40-9a3a-2c9b2f9d3c1a.

3. Back up the state before touching anything. Run terraform state pull (a read that does not need the lock) and save a timestamped copy, noting its serial and lineage. With S3 versioning, list the object versions to see whether a new version was written after the lock was created (14:03:11 UTC), which tells us whether the apply persisted state. Check the runner's workspace for an errored.tfstate file: Terraform writes it locally when it cannot push state to the backend, and it may be the only record of what was created.

4. Find out what actually changed in AWS. Retrieve the saved plan artifact of that CI run (main @ abc123) to know what the apply intended to do. Use AWS CloudTrail to list the API calls made by the CI role between 14:03 UTC and the timeout (Create*, Delete*, Modify*, Update*). Compare what was intended, what happened in AWS, and what is recorded in the state backup.

5. Decide whether force-unlock is acceptable. Only if ALL of these are true: the process holding the lock is confirmed dead (job terminated and runner process gone, or runner destroyed); the state is backed up and any errored.tfstate is secured; we have a clear picture of what changed in AWS; the Lock ID matches exactly the stuck CI run and nobody else is operating; and the incident owner approves and records it. Only then, from the controlled admin environment: terraform force-unlock 4f7e0a7b-2b7b-4f40-9a3a-2c9b2f9d3c1a. If any condition fails, we wait.

6. Reconcile the state with reality before any new apply. Run terraform plan -refresh-only to see the drift without changing anything. If a valid, newer errored.tfstate exists, review it and restore it with terraform state push (after checking serial and lineage). If resources were created in AWS but are missing from state, bring them in with import blocks or terraform import instead of re-applying, which would try to create them again and cause duplicates or name conflicts. Repeat until a normal terraform plan shows only the expected changes from abc123.

7. Resume through the normal path and close the loop. Re-enable the pipeline and let CI, not a manual apply, run the remaining changes from a fresh, reviewed plan. Monitor the affected services and write a short blameless postmortem: timeline, what changed, and why the job timed out.

ONE CHANGE TO PREVENT THIS: Make CI stop Terraform gracefully instead of killing it. Set the CI job timeout comfortably above Terraform's longest expected apply (EKS node group operations can take 30+ minutes), and on timeout or cancellation send SIGINT with a grace period before killing the job. Terraform will then finish in-flight operations, write the state and release the lock itself, instead of leaving an orphaned lock and an unknown state. On failure, the same job should always upload errored.tfstate and the plan file as artifacts.
```

## Pregunta 3 - Drift por un CIDR agregado a mano durante un incidente (`10.55.8.0/24`)

```text
First, I would reject the broad lifecycle ignore_changes proposal. It turns this security group into a permanent blind spot: Terraform would silently accept any future manual change to its ingress, including an accidental or malicious 0.0.0.0/0. It also leaves the emergency fix undocumented, so nobody reading the code would know 10.55.8.0/24 exists, why, or who approved it. Drift is a signal; the goal is to make Terraform the source of truth again, not to silence the signal.

At the same time, nobody should run a normal apply on this area right now: Terraform would remove 10.55.8.0/24 and most likely bring back the outage.

1. WHAT I NEED TO VERIFY TO DECIDE THE DESIRED RULE

- Exactly what was changed: find the AuthorizeSecurityGroupIngress event around 02:14 UTC in CloudTrail. Who made it, and which protocol and ports were opened? The incident note only mentions the CIDR; if it opened all ports instead of only the health-check/listener port, it is broader than necessary.
- What 10.55.8.0/24 actually is: it is outside the VPC's expected range (10.20.0.0/16). Is it a peered VPC or Transit Gateway network, a VPN/on-prem range, a monitoring platform, or a new secondary CIDR/subnet in the VPC? Check route tables, subnet inventory and IPAM records, and identify the owning team.
- Whether the traffic is real: use VPC Flow Logs to see which source IPs in 10.55.8.0/24 actually reach the load balancer, and on which ports. This tells me whether the whole /24 is needed or only a narrower range.
- The root cause: why did health checks start failing at 02:14? Something changed (new subnet, migration, new health-checking system). The rule may be the correct permanent fix, or a patch over another problem that should be fixed elsewhere.
- Whether it can be expressed more safely: if the source has its own security group in the same VPC/region, a security-group reference is more precise than a CIDR.
- Approval: the service owner and Security agree on the final rule, whether it is permanent or temporary (with an expiry date), and how narrow it is.

2. FIRST ACTIONS IN TERRAFORM/AWS TO RECONCILE SAFELY

- Freeze production applies that touch this security group or module until reconciliation is merged, and communicate it to the team, because the next routine apply would revert the fix.
- Leave AWS as it is: the emergency rule stays in place while we investigate. No manual removal.
- Codify the fix in Terraform: open a PR that adds the agreed rule to the configuration, with a comment linking the incident ticket, for example: ingress_cidrs = ["10.20.0.0/16", "10.55.8.0/24"] # INC-XXXX: health checks from <owner/system>, added 02:14 UTC, approved by Security. Acceptance criterion: terraform plan shows no changes for this security group. If rules are modeled as separate resources (aws_vpc_security_group_ingress_rule / aws_security_group_rule), bring the manual rule into state with an import block instead of creating a duplicate.
- If the desired rule is narrower than the emergency one (fewer ports, smaller CIDR, or a security-group reference), apply it as a deliberate "add before remove" change: add the narrow rule first, confirm through flow logs and target health that health checks still pass, and only then remove the broad emergency rule in a separate apply. That way there is never a window without health-check access.
- If the rule is temporary, record its expiry date and owner in the ticket, and plan its removal once the root cause is fixed.

3. SAFEGUARDS BEFORE THE NEXT PRODUCTION RUN TOUCHES THIS AREA

- Plan review guardrail: production plans that remove or modify ingress rules on this security group (or any load balancer security group) require explicit approval from the service owner, for example through CODEOWNERS on the module.
- Policy-as-code in CI (OPA/Conftest, Checkov or Sentinel): block 0.0.0.0/0 and all-ports rules on internal load balancers, and require a justification/ticket tag for new CIDRs.
- Scheduled drift detection, for example a nightly terraform plan -detailed-exitcode in CI or Terraform Cloud/Spacelift drift detection, alerting the owning team so the next emergency change is detected within hours.
- AWS Config rules or an EventBridge alert on security group changes made outside the CI role, so every manual change is visible immediately.
- A stronger break-glass process: every manual emergency change must open a follow-up ticket to codify it in Terraform within a defined time (for example 24-48 hours), with the exact change details. Emergency changes should go through a dedicated break-glass role whose use is logged and alerted.
- If an ignore_changes is ever unavoidable, it must be narrow (one specific attribute), documented and time-limited, never a blanket ignore on a security resource.

In summary: I would neither ignore the drift nor blindly revert it. I would verify what the emergency rule really is and who needs it, codify the right version in Terraform so the plan comes back clean, and add drift detection and break-glass follow-ups so manual fixes become code within a day.
```

## Pregunta 4 (video, 60 s) - Stakeholder pide `apply -auto-approve`, force-unlock y `-target` hoy

**Ideas:**

```text
1. Urgent → I want it today
2. No shortcuts → outage risk
3. auto-approve = no review | force-unlock = corrupt state | -target = half-applied
4. Pipeline → plan review 30 min → apply via CI today → monitor
5. Surprises → risk + new ETA → ship today, safely
```

**Libreto:**

> "I understand this is urgent, and I want to get it out today. But I won't take those shortcuts, because each one can turn a small change into a production outage.
>
> Auto-approve means applying something nobody has reviewed. Force-unlocking a running apply can corrupt our state. And `-target` leaves the state half-applied, which usually breaks the next deployment.
>
> Here's what I propose: I'll push the change through our normal pipeline right now, review the plan with a teammate within the next thirty minutes, and if it only touches the node group as expected, we apply it today through CI, while I monitor the service.
>
> If the plan shows anything unexpected, I'll tell you right away with the specific risk and a new ETA. That way we ship today, without putting customers at risk."
