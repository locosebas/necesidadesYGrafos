MCP y A2A

MCP (Model Context Protocol): cómo funciona

  • Estándar abierto de Anthropic para conectar un LLM a herramientas y datos
  • Host (la app) → cliente MCP (uno por servidor) ↔ servidor MCP
  • Mensajes JSON-RPC 2.0 · transportes stdio (local) y Streamable HTTP (remoto)
  • El servidor expone tools (acciones), resources (datos) y prompts (plantillas)
  • El cliente puede ofrecer sampling, roots y elicitation · seguridad remota con OAuth 2.1
Guion: MCP, Model Context Protocol, es un estándar abierto que creó Anthropic para conectar modelos con herramientas y datos de una forma uniforme. Hay un host, que es la aplicación de IA, y dentro del host hay un cliente MCP por cada servidor MCP. Hablan en JSON-RPC 2.0, ya sea por stdio si es local o por Streamable HTTP si es remoto, y en ese caso con OAuth 2.1. El servidor expone tres cosas: tools, que son acciones; resources, que son datos para leer, y prompts, que son plantillas. La gran ventaja es que pasas de integrar N modelos por M herramientas a que cada herramienta se integre una sola vez.

También limitábamos el tamaño de las respuestas y auditábamos cada llamada.
MCP y A2A

A2A (Agent-to-Agent): cómo funciona

  • Protocolo abierto que lanzó Google (2025), hoy en la Linux Foundation
  • Agent Card: JSON público con las skills, la URL y la autenticación del agente
  • JSON-RPC 2.0 sobre HTTPS · SSE (Server-Sent Events) para streaming · webhooks para push
  • Task con estados: submitted → working → input-required → completed / failed / canceled
  • Resultado en Artifacts con parts (texto, archivo, datos) · los agentes son opacos
Guion: A2A, Agent-to-Agent, es un protocolo abierto que lanzó Google en 2025 y que ahora está en la Linux Foundation. Cada agente publica una Agent Card, un JSON que dice qué sabe hacer, dónde está y cómo autenticarse. El agente cliente descubre esa Agent Card y le manda una tarea por JSON-RPC sobre HTTPS. La tarea pasa por estados, y uno importante es input-required, cuando el agente remoto necesita algo más. El avance llega por streaming con SSE o por webhooks, y el resultado llega como artifacts. Los agentes son opacos: no comparten su memoria ni sus herramientas internas, solo el contrato.
MCP y A2A

P3 · "¿Cuál es la diferencia entre MCP y A2A?"

  • MCP = agente ↔ herramienta (vertical): el agente usa una capacidad
  • A2A = agente ↔ agente (horizontal): el agente delega una tarea a otro agente autónomo
  • Son complementarios: cada agente usa MCP por dentro y A2A para hablar con otros
  • A2A sirve cuando otro equipo u otro proveedor es dueño del agente
  • Si todo está en un solo servicio, basta con un supervisor en LangGraph (sin red de por medio)
Guion: MCP conecta un agente con herramientas y datos: el agente llama una tool y recibe un resultado. A2A conecta agentes entre sí: el agente delega una tarea completa a otro agente que razona por su cuenta y puede pedir más información. Son complementarios: cada agente usa MCP por dentro para sus herramientas y A2A hacia afuera para coordinarse. Yo usaría A2A cuando el otro agente es de otro equipo o de otro proveedor. Si todos los agentes viven en el mismo servicio, un supervisor dentro de LangGraph es más simple y no pagas la latencia de la red.
Arquitectura

P4 · "Diseña un sistema multiagente para un negocio"

  • 1 · Entender el problema: qué tarea, qué métrica de éxito y qué riesgo tiene equivocarse
  • 2 · Entrada: API FastAPI con validación Pydantic y streaming SSE
  • 3 · Orquestación: supervisor con estado y checkpoints (LangGraph) → agentes especialistas
  • 4 · Integración: herramientas por MCP y agentes de otros equipos por A2A
  • 5 · Control: guardarraíles, aprobación humana para acciones de riesgo, observabilidad (trazas, costo, calidad)
Guion: Primero pregunto qué problema resolvemos, cómo medimos el éxito y qué tan grave es que el agente se equivoque, porque eso define cuánta autonomía le doy. La entrada sería una API en FastAPI que valida con Pydantic y devuelve streaming por SSE. Detrás, un agente supervisor con estado persistente, por ejemplo en LangGraph con checkpointer en Postgres, que reparte el trabajo a agentes especialistas. Las herramientas del negocio, como CRM o tickets, entran por servidores MCP, y los agentes que son de otros equipos se conectan por A2A. Encima, guardarraíles, aprobación humana para lo riesgoso y observabilidad con trazas, costo por token y evaluación. Todo corre en Kubernetes con el CI/CD de siempre.
Arquitectura

P5 · "¿Cómo haces seguro un flujo autónomo en producción?"

  • Autonomía por niveles: leer = automático · escribir = con aprobación · irreversible = siempre humano
  • Menor privilegio: cada agente con sus credenciales y solo sus tools
  • Límites: máximo de pasos, timeouts, presupuesto de tokens y costo por tarea
  • Idempotencia y reintentos seguros · auditoría de cada decisión y cada llamada
  • Prompt injection: tratar el contenido externo como datos, nunca como instrucciones · validar salidas con Pydantic
Guion: Lo pienso por niveles de autonomía: leer información puede ser automático, escribir necesita aprobación, y lo irreversible siempre lo aprueba una persona. Así lo teníamos en el triage. Cada agente tiene sus propias credenciales y solo las tools que necesita. Pongo límites de pasos, timeouts y presupuesto de tokens para que un agente no se quede en un ciclo infinito gastando plata. Las acciones son idempotentes para que reintentar sea seguro, y todo queda auditado. Y contra el prompt injection, lo que viene de afuera se trata como dato, y las salidas del modelo se validan con Pydantic antes de ejecutar nada.
Frameworks

  • LlamaIndex: centrado en datos y RAG: Documents → Nodes → Index → query engine
  • AutoGen (Microsoft): agentes que conversan entre sí (group chat) · su sucesor es el Microsoft Agent Framework
  • CrewAI: agentes por roles (role, goal, backstory) que cumplen Tasks dentro de una Crew
  • Cuándo cuál: control fino → LangGraph · RAG pesado → LlamaIndex · roles rápidos → CrewAI
Guion: LangChain da las piezas básicas para trabajar con LLM, y LangGraph, que es de los mismos creadores, modela el agente como un grafo con estado, que es lo que más se usa en producción porque te da control. LlamaIndex está más enfocado en datos y RAG: carga documentos, los parte en nodos, crea índices y consulta. AutoGen, de Microsoft, se basa en agentes que conversan entre sí, y Microsoft lo está unificando con Semantic Kernel en el Microsoft Agent Framework. CrewAI organiza agentes por roles, cada uno con un objetivo, que cumplen tareas dentro de un equipo, o crew. Si necesito control fino y aprobación humana, elijo LangGraph.
Frameworks

LangChain: las piezas

  • Chat model (ChatAnthropic, ChatOpenAI): misma interfaz para cualquier proveedor de LLM
  • Prompt template (ChatPromptTemplate) · tools (@tool, .bind_tools()) · retrievers para RAG
  • Structured output: .with_structured_output(ModeloPydantic), como tu diagnóstico del triage
  • LCEL (LangChain Expression Language): prompt | modelo | parser · todo es Runnable: invoke, ainvoke, stream, batch
  • langchain-mcp-adapters: tus servidores MCP como tools · en LangChain 1.0 create_agent corre sobre LangGraph
Guion: LangChain es la caja de piezas: modelos, prompts, tools, retrievers y salida estructurada. Las piezas se encadenan con LCEL usando un pipe, como en Linux: prompt, luego modelo, luego parser. Todas las piezas de LangChain son Runnables, así que tienen invoke y también ainvoke, que es la versión asíncrona. Con langchain-mcp-adapters cargo mis servidores MCP como tools. Y desde LangChain 1.0, los agentes se crean con create_agent, que por debajo corre sobre LangGraph.
Frameworks

LangGraph: los 5 conceptos

  • 1 · State: un TypedDict con lo que viaja por el grafo (ticket, servicio, diagnóstico)
  • 2 · Nodes: funciones que reciben el estado y devuelven solo lo que cambiaron
  • 3 · Edges: add_edge y add_conditional_edges (decisiones y ciclos)
  • 4 · Checkpointer: guarda el estado en cada paso (MemorySaver, PostgresSaver) por thread_id
  • 5 · interrupt(): pausa para la aprobación humana · se retoma con Command(resume=...)
  • Extras: ToolNode + tools_condition (ciclo ReAct) · supervisor y subgrafos · stream · trazas en LangSmith
Guion: LangGraph controla el flujo como un grafo con estado. El estado es un TypedDict. Los nodos son funciones que devuelven solo lo que cambiaron. Las aristas condicionales deciden el camino y permiten ciclos, como volver a leer logs si faltan datos. El checkpointer guarda el estado en cada paso por thread_id, así el grafo se puede pausar, retomar y sobrevivir a un reinicio. Y interrupt pausa el grafo para la aprobación humana, que se retoma con Command resume. Mi triage se traduce uno a uno: cada paso es un nodo, aprobar o reenrutar es una arista condicional y la aprobación es un interrupt. Uso LangChain solo para una cadena lineal, y LangGraph cuando hay ciclos, estado o aprobación humana.
Frameworks

LlamaIndex: el framework de datos para RAG

  • Readers (SimpleDirectoryReader, conectores de LlamaHub, LlamaParse para PDF) → Documents
  • Node parser (SentenceSplitter) → Nodes · todo en un IngestionPipeline
  • VectorStoreIndex sobre pgvector, OpenSearch, etc. → retriever (top-k + reranker)
  • index.as_query_engine() responde · chat engine para conversación
  • Agentes: FunctionAgent, AgentWorkflow · Workflows por eventos con @step
Guion: LlamaIndex es el framework más fuerte en datos y RAG. Los readers cargan documentos, y para PDF difíciles está LlamaParse. El node parser los parte en nodes, el VectorStoreIndex guarda los embeddings en una base vectorial, el retriever trae los top-k con un reranker y el query engine arma la respuesta. Para agentes tiene FunctionAgent y AgentWorkflow, y los Workflows son pasos que reaccionan a eventos. Si mi problema es sobre todo buscar en documentos, como los runbooks del triage, elijo LlamaIndex.
Frameworks

CrewAI: un equipo de agentes por roles

  • Agent: role, goal, backstory, tools y LLM
  • Task: description, expected_output, el agente que la hace, context=[otra_task], output_pydantic
  • Crew: agentes + tareas + Process: sequential o hierarchical (un manager delega)
  • crew.kickoff(inputs={...}) · human_input=True en una Task para la aprobación humana
  • Flows: control por eventos (@start, @listen, @router) cuando necesitas más control
Guion: CrewAI organiza agentes como un equipo de trabajo. Cada Agent tiene un rol, un objetivo y una historia de fondo, que es su personalidad dentro del prompt. Cada Task tiene una descripción y la salida esperada, y puede usar el resultado de otra tarea como contexto. La Crew junta agentes y tareas con un proceso secuencial, o jerárquico si un manager reparte el trabajo. Se lanza con kickoff. Es el más rápido para armar un prototipo multiagente, y cuando necesitas más control usas Flows.
Frameworks

AutoGen (Microsoft): agentes que conversan

  • AgentChat: AssistantAgent (LLM + tools) y UserProxyAgent (la persona)
  • Teams: RoundRobinGroupChat (por turnos), SelectorGroupChat (un LLM elige quién habla), Swarm (handoffs)
  • Termination: TextMentionTermination("APPROVE"), MaxMessageTermination
  • Core: modelo de actores asíncronos que se mandan mensajes (puede ser distribuido) · todo es async
  • Sucesor: Microsoft Agent Framework (AutoGen + Semantic Kernel, desde octubre de 2025)
Guion: AutoGen, de Microsoft, modela el trabajo como una conversación entre agentes. Un AssistantAgent es un LLM con tools, y el UserProxyAgent representa a la persona. Los agentes se organizan en equipos: por turnos con RoundRobinGroupChat, con un LLM que elige quién habla con SelectorGroupChat o con traspasos con Swarm. La conversación termina con una condición, por ejemplo cuando alguien dice APPROVE. Por debajo está AutoGen Core, un modelo de actores asíncronos. Microsoft lo está unificando con Semantic Kernel en el Microsoft Agent Framework, y eso vale la pena mencionarlo.

Frameworks

Diferencias: equivalentes de LangGraph (1/2)

  • Semantic Kernel (Microsoft): empresas en .NET, C# y Python, con "plugins" en vez de grafo · se une con AutoGen en el Microsoft Agent Framework
  • Haystack (deepset): pipelines de componentes · más fuerte en búsqueda y RAG que en agentes con ciclos
  • Pydantic AI: tipado fuerte, la salida del agente es un modelo Pydantic · más simple que LangGraph
  • DSPy (Stanford): no escribes prompts: declaras qué entra y qué sale, y DSPy optimiza el prompt

Guion: La diferencia de fondo es cuánto control te da cada uno. LangGraph te da control total del flujo con un grafo. Semantic Kernel es la opción de Microsoft para empresas en .NET. Haystack es más de pipelines de búsqueda. Pydantic AI apuesta por tipado fuerte y simplicidad. DSPy cambia el enfoque: en vez de escribir prompts, los optimiza. Y smolagents hace que el agente escriba código como acción.

Infraestructura

¿Dónde corren los agentes? Las 4 opciones

  • Administrado: AWS Bedrock AgentCore · Google Vertex AI Agent Engine · Azure AI Foundry Agent Service
  • AgentCore: corre tu agente (LangGraph, CrewAI, Strands…) con Runtime (sesiones aisladas), Memory, Gateway (APIs y Lambdas como tools MCP), Identity y Observability
  • Kubernetes (EKS, AKS, GKE): máximo control, el mismo CI/CD y observabilidad de siempre · tu terreno
  • Contenedores serverless: Cloud Run, ECS Fargate, Azure Container Apps · sin administrar nodos
  • Lambda: solo para tools y servidores MCP cortos (límite de 15 minutos), no para el agente completo
Guion: Hay cuatro lugares. Los runtimes administrados de cada nube: Bedrock AgentCore en AWS, Vertex AI Agent Engine en Google Cloud y AI Foundry Agent Service en Azure. Tú traes el agente y ellos ponen el runtime, la memoria, la identidad y la observabilidad. Si la empresa quiere control total, Kubernetes, con el mismo CI/CD y la misma observabilidad de siempre, que es mi experiencia. Un punto medio son los contenedores serverless como Cloud Run o ECS Fargate. Y Lambda sirve para las tools o los servidores MCP, no para un agente que puede tardar minutos.
Infraestructura

Dónde vive cada pieza (ejemplo en AWS)

  • Entrada: API Gateway o ALB → FastAPI en EKS / ECS Fargate, o AgentCore Runtime
  • Estado: RDS Postgres como checkpointer de LangGraph + pgvector para RAG
  • Tareas largas: SQS + workers, para no dejar una petición HTTP abierta minutos
  • Tools: servidores MCP en Lambda o contenedores, publicados con AgentCore Gateway
  • Modelos: Amazon Bedrock (Claude incluido) · observabilidad: CloudWatch / Datadog con OpenTelemetry
  • Hogar natural: ADK → Vertex · Strands → AgentCore · Microsoft Agent Framework → Azure Foundry · LangGraph / CrewAI → cualquiera
Guion: En AWS lo armaría así. Entra por API Gateway o un ALB a una API FastAPI en EKS o ECS Fargate, o directo a AgentCore Runtime si queremos menos operación. El estado del agente vive en Postgres como checkpointer de LangGraph, y el mismo Postgres con pgvector sirve para RAG. Las tareas largas van por SQS con workers. Las tools son servidores MCP en Lambda o contenedores, y los modelos vienen de Bedrock, que incluye Claude. Todo trazado con OpenTelemetry hacia CloudWatch o Datadog. Cada framework tiene su nube natural: ADK en Vertex, Strands en AgentCore, el Microsoft Agent Framework en Azure, y LangGraph o CrewAI corren en cualquier parte.

asyncio: la idea y los 6 conceptos

  • Idea: muchas esperas a la vez en un solo hilo · ideal para I/O-bound (LLM, APIs, BD, MCP), no para CPU pesada
  • 1 · Event loop (asyncio.run) · 2 · Coroutine (async def) · 3 · await: "mientras espero, atiende a otro"
  • 4 · Task (create_task) · 5 · TaskGroup (cancela las demás si una falla) o gather(return_exceptions=True)
  • 6 · Control: Semaphore(n) para el rate limit · asyncio.timeout(s) · reintentos con await asyncio.sleep(2 ** intento)
  • Resultado: 10 llamadas de 3 s → ~30 s en secuencia, ~6 s con Semaphore(5)
Guion: asyncio permite que un solo hilo atienda muchas esperas al tiempo con un event loop. Es como un mesero que, mientras la cocina prepara un plato, atiende otra mesa. Una función async def es una corrutina, y await le dice al event loop "mientras espero, atiende a otro". Lanzo varias tasks en paralelo con un TaskGroup, que cancela las demás si una falla, y controlo con un Semaphore para no pasarme del rate limit del proveedor, timeouts y reintentos con backoff exponencial. Sirve para esperas de red, como llamar a un LLM, pero no para CPU pesada.

asyncio: llamadas concurrentes al LLM, paso a paso

  • Un solo cliente: async with httpx.AsyncClient() as cliente (o AsyncAnthropic), abierto una vez, en FastAPI en el lifespan
  • Paralelo: async with asyncio.TaskGroup() as tg: → tg.create_task(llamar_llm(cliente, p))

  • Nunca colgado: async with asyncio.timeout(30): → await cliente.post(...)

Guion: En inglés: asyncio lets one thread handle many I/O waits concurrently through an event loop, which is perfect for LLM calls. For concurrent calls I use a TaskGroup, a Semaphore to respect the provider's rate limit, timeouts, and retries with exponential backoff. In FastAPI I never block inside an async def endpoint: I use async clients opened once in the lifespan, and asyncio.to_thread for anything blocking.

P8 · "¿Errores comunes con asyncio?"

  • Bloquear el event loop: requests o time.sleep dentro de async def → usar httpx.AsyncClient, asyncio.sleep
  • Código que bloquea sí o sí → asyncio.to_thread o un worker aparte
  • async def vs def en FastAPI: def corre en un threadpool; async def corre en el loop (no bloquear)
  • gather vs TaskGroup: TaskGroup cancela todas las demás si una falla
  • I/O-bound (LLM, red) = asyncio ✅ · CPU-bound (embeddings locales) = procesos o workers
Guion: El error más común es bloquear el event loop: usar requests o time.sleep dentro de una función async, porque eso congela todas las demás peticiones. Se usa httpx.AsyncClient y asyncio.sleep, y si algo bloquea sí o sí, se manda a un hilo con asyncio.to_thread. En FastAPI, un endpoint def normal corre en un threadpool y uno async def corre en el event loop, así que en el async no puedes bloquear. TaskGroup es mejor que gather porque si una tarea falla, cancela las demás. Y asyncio sirve para trabajo de entrada y salida, como llamar a un LLM, pero no para CPU pesada.

Pydantic: qué es y sus piezas

  • Idea: validar y convertir datos usando los type hints de Python · núcleo en Rust (pydantic-core), muy rápido
  • BaseModel con tipos · Field(ge=0, le=1, min_length=1, description=...) · Literal, Enum, modelos anidados
  • @field_validator (un campo) · @model_validator (varios campos) · ConfigDict(extra="forbid", strict=True)
  • Entrar: model_validate / model_validate_json · salir: model_dump / model_dump_json · model_json_schema()
  • Falla → ValidationError con e.errors() · configuración con pydantic-settings (BaseSettings)
Guion: Pydantic valida y convierte datos a partir de los type hints de Python, y su núcleo está escrito en Rust, así que es muy rápido. Defino un BaseModel con tipos, uso Field para las reglas como rangos o longitudes, y validators cuando la regla es más compleja. Con extra forbid rechazo campos que no esperaba. Los datos entran con model_validate o model_validate_json, salen con model_dump, y model_json_schema genera el JSON schema. Si algo no cumple, lanza ValidationError con el detalle de cada error.
