  • Remote backend with locking (GCS, Azure Blob, S3)
  • Differences go in variables, not duplicated code
  • Módulos pequeños, versionados con tags; cada ambiente fija una versión
  • Un state por ambiente y componente → menor blast radius (radio de impacto)
  • Backend remoto con locking (bloqueo) (GCS, Azure Blob, S3)
  • Las diferencias van en variables, no en código duplicado
🇺🇸 Say it (EN): I separate modules from environments. Every environment and component has its own state in a remote backend with locking, which reduces the blast radius. Differences between environments are variables, never copied code. At Mercado Libre our shared modules were used by many teams, so versioning was critical.
🇨🇴 Guion (ES): Separo los módulos de los ambientes. Q9 · Terraform vs. Ansible · Terraform contra Ansible

  • Terraform: declarative, keeps state, provisions infrastructure
  • Ansible: agentless (SSH / WinRM), configures what already exists
  • Ansible is idempotent: ok vs. changed; reusable roles
  • Together: Terraform creates the VM → Ansible configures OS, packages, patches
  • Terraform: declarativo, guarda state, aprovisiona la infraestructura
  • Ansible: agentless (sin agente) (SSH / WinRM), configura lo que ya existe
  • Ansible es idempotente: ok contra changed; roles reutilizables
  • Juntos: Terraform crea la VM → Ansible configura sistema operativo, paquetes y parches
🇺🇸 Say it (EN): Terraform is for provisioning: it's declarative and keeps state, so it knows what exists and what to change. Ansible is for configuration: it's agentless, connects over SSH to Linux or WinRM to Windows, and runs idempotent tasks, so running it twice gives the same result. They work together: Terraform creates the virtual machines and the network, and Ansible configures the operating system, installs packages and applies patches, which matters a lot at Chubb because the role includes Windows and Linux.
🇨🇴 Guion (ES): Terraform es para aprovisionar: es declarativo y guarda state, así que sabe qué existe y qué cambiar. Ansible es para configurar: es agentless, se conecta por SSH a Linux o por WinRM a Windows, y corre tareas idempotentes, así que correrlo dos veces da el mismo resultado. Trabajan juntos: Terraform crea las máquinas virtuales y la red, y Ansible configura el sistema operativo, instala paquetes y aplica parches, lo que importa mucho en Chubb porque el cargo incluye Windows y Linux.

Q10 · Kubernetes architecture · Arquitectura de Kubernetes

  • Control plane: kube-apiserver, etcd, kube-scheduler, kube-controller-manager, cloud-controller-manager
  • Worker node: kubelet, kube-proxy, container runtime (containerd)
  • Everything goes through the API server
  • Core idea: the reconciliation loop (desired state vs. actual state)
  • Control plane: kube-apiserver, etcd, kube-scheduler, kube-controller-manager, cloud-controller-manager
  • Worker node: kubelet, kube-proxy, container runtime (containerd)
  • Todo pasa por el API server
  • Idea central: el reconciliation loop (estado deseado contra estado real)
🇺🇸 Say it (EN): Kubernetes has a control plane and worker nodes. The control plane has the API server, the front door for everything; etcd, the key-value store with the state; the scheduler, which decides on which node each Pod runs; the controller manager, which runs the reconciliation loops; and the cloud controller manager, which talks to the cloud provider for load balancers and disks. On each worker, the kubelet makes sure the Pods are running, kube-proxy programs the network rules for Services, and containerd runs the containers. In AKS, EKS or GKE the provider manages the control plane for you.
🇨🇴 Guion (ES): Kubernetes tiene un control plane y worker nodes. El control plane tiene el API server, la puerta de entrada para todo; etcd, la base clave-valor con el estado; el scheduler, que decide en qué nodo corre cada Pod; el controller manager, que corre los reconciliation loops; y el cloud controller manager, que habla con el proveedor cloud para balanceadores y discos. En cada worker, el kubelet se asegura de que los Pods estén corriendo, kube-proxy programa las reglas de red de los Services y containerd corre los contenedores. En AKS, EKS o GKE el proveedor administra el control plane por ti.

Q11 · AKS vs. EKS vs. GKE · Diferencias entre AKS, EKS y GKE

  • Same Kubernetes API; the difference is the integration with each cloud
  • Identity: Entra ID + Workload Identity (AKS), IAM + IRSA / Pod Identity (EKS), Workload Identity (GKE)
  • Networking: Azure CNI, VPC CNI, VPC-native
  • GKE Autopilot: Google also manages the nodes
  • La misma API de Kubernetes; la diferencia es la integración con cada nube
  • Identidad: Entra ID + Workload Identity (AKS), IAM + IRSA / Pod Identity (EKS), Workload Identity (GKE)
  • Red: Azure CNI, VPC CNI, VPC-native (CNI: Container Network Interface)
  • GKE Autopilot: Google también administra los nodos
🇺🇸 Say it (EN): The Kubernetes API is the same, so manifests and Helm charts are portable. What changes is the integration: identity, networking, load balancers and upgrades. In AKS, identity comes from Entra ID and pods use Workload Identity; in EKS, IAM roles for service accounts or Pod Identity; in GKE, Workload Identity too.
