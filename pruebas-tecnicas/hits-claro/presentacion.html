Panorama

Panorama: CI vs CD

  • CI (Continuous Integration): cada cambio se integra, compila, prueba y analiza automáticamente
  • CD (Continuous Delivery): la versión queda lista para producción; el paso a producción lleva aprobación
  • Continuous Deployment: lo mismo, pero sin aprobación humana
  • DevSecOps: la seguridad va dentro del pipeline (shift-left), no al final
Guion: CI, Continuous Integration, responde a la pregunta: ¿este cambio está bien hecho? Compila, pasa las pruebas, pasa el quality gate y los escaneos de seguridad. CD, Continuous Delivery, responde: ¿esta versión puede llegar a producción de forma segura? En Continuous Delivery hay una aprobación antes de producción; en Continuous Deployment no la hay. En una empresa como Claro, con control de cambios, lo normal es Continuous Delivery.
Panorama

Los 11 pasos de punta a punta

  • CI: 1 commit y PR · 2 build y pruebas unitarias · 3 quality gate · 4 seguridad del código · 5 imagen firmada
  • CD: 6 IaC escaneada · 7 deploy en stage · 8 pruebas en stage · 9 gate y aprobación · 10 producción progresiva · 11 observar y rollback
  • Cada paso puede detener el pipeline: fallar rápido y barato
Guion: El pipeline tiene dos mitades. La mitad de CI termina con un artefacto inmutable, escaneado y firmado. La mitad de CD toma ese mismo artefacto y lo lleva por stage hasta producción. Cada paso es un control: si falla, el pipeline se detiene, y entre más temprano falla, más barato sale corregir.
Panorama

Regla de oro: build once, deploy anywhere

  • La versión se crea una sola vez; nunca se recompila por ambiente
  • Se identifica por versión semántica + digest de la imagen
  • Stage va unos días antes; para pasar a producción hay que demostrar que stage está sano
  • La configuración por ambiente va fuera del artefacto (values, variables, secretos)
Guion: Así trabajábamos en Bizagi y en MercadoLibre: un paso crea la versión, el artefacto, y otro paso la despliega. Primero en stage, se deja correr unos días, se muestra la evidencia de que no hay problemas, y solo ahí va a los varios ambientes de producción. Lo que llega a producción es exactamente lo que se probó.
CI · Continuous Integration

Paso 1 · Commit y pull request

  • Git + ramas cortas (trunk-based development)
  • pre-commit hooks: linter y Gitleaks antes de subir
  • Pull Request / Merge Request con revisores obligatorios
  • Branch protection: no hay merge sin los checks del pipeline en verde
  • Herramientas: GitHub, GitLab, Azure Repos, Bitbucket
Guion: El aseguramiento empieza antes del pipeline. En la máquina del desarrollador, los pre-commit hooks corren el linter y Gitleaks para que un secreto nunca llegue al repositorio. Después, el pull request dispara el pipeline, y la branch protection impide el merge si algún check falla o si falta la revisión de otro par.
CI · Continuous Integration

Paso 2 · Build y pruebas unitarias

  • Compilar con caché de dependencias: Maven, Gradle, npm, dotnet, go build
  • Pruebas unitarias: JUnit, pytest, Jest, xUnit, go test
  • Cobertura: JaCoCo, Coverage.py, Istanbul/nyc
  • Orquestadores: Jenkins, GitLab CI, Azure Pipelines, GitHub Actions
Guion: El build compila y corre las pruebas unitarias. Si una prueba falla, el pipeline se detiene ahí. El reporte de cobertura, por ejemplo de JaCoCo en Java, no se queda en el job: se envía al quality gate del paso siguiente. He integrado pruebas automatizadas en pipelines de Azure Pipelines, Jenkins y GitLab CI.
CI · Continuous Integration

Paso 3 · Aseguramiento de calidad: quality gate

  • SonarQube / SonarCloud: bugs, code smells, vulnerabilidades, security hotspots, duplicación
  • Quality gate sobre el código nuevo ("clean as you code"): ej. cobertura ≥ 80 %, 0 bugs nuevos, 0 vulnerabilidades
  • Decoración del pull request con los hallazgos
  • Alternativas: Codacy, Code Climate, SonarLint en el IDE
Guion: El quality gate es la regla de aseguramiento de código: un umbral que, si no se cumple, rompe el pipeline. El estándar de la industria es SonarQube. La buena práctica es aplicar el quality gate solo al código nuevo, así un proyecto legado puede mejorar poco a poco sin bloquear al equipo. SonarQube lo conozco como estándar y lo estoy reforzando; lo que sí he hecho es poner checks obligatorios que bloquean el merge.
CI · Continuous Integration

Paso 4 · Seguridad del código

  • SAST (Static Application Security Testing): Semgrep, Checkmarx, Fortify, SonarQube
  • SCA (Software Composition Analysis): Snyk, OWASP Dependency-Check, Dependabot, Trivy
  • Secretos: Gitleaks, TruffleHog, GitHub secret scanning
  • SBOM (Software Bill of Materials): Syft, CycloneDX
  • Política: falla con Critical / High; hallazgos en DefectDojo
Guion: Se corren cuatro escaneos en paralelo. SAST revisa nuestro código buscando inyecciones o malas prácticas. SCA revisa las librerías de terceros contra bases de vulnerabilidades conocidas, los CVE. El escaneo de secretos busca llaves en el código. Y el SBOM es el inventario de todo lo que trae la aplicación. Una política define qué severidad rompe el pipeline, normalmente Critical y High.
CI · Continuous Integration

Paso 5 · Empaquetar, escanear y firmar la imagen

  • Docker multi-stage + imagen base distroless o mínima
  • Escaneo de imagen: Trivy, Grype
  • Firma y atestación: Cosign (Sigstore), SBOM adjunto, niveles SLSA
  • Registro: JFrog Artifactory, Nexus, Harbor, ECR, ACR
  • El clúster verifica la firma antes de correr la imagen
Guion: Este es el final de CI: la imagen se construye en varias etapas para que en producción no queden compiladores ni herramientas. Trivy la escanea; si hay vulnerabilidades críticas, no se publica. Cosign la firma, y en el clúster una política de Kyverno solo deja correr imágenes firmadas por nuestro pipeline. Eso es seguridad de la cadena de suministro.
CD · Continuous Delivery

Paso 6 · Infraestructura como código segura

  • Terraform por pull request: el plan se revisa antes del apply
  • Escaneo de IaC: Checkov, Trivy (antes tfsec), KICS
  • Políticas como código: OPA (Open Policy Agent) / Conftest, Sentinel
  • Estado remoto con bloqueo (S3 + DynamoDB, Azure Storage)
Guion: La infraestructura pasa por el mismo rigor que el código. El pull request con cambios de Terraform genera el plan, Checkov o Trivy buscan configuraciones inseguras, como un bucket público o un puerto 22 abierto a internet, y una persona revisa el plan antes del apply. Esto lo hice con GitHub Actions: plan en el pull request, apply después de la aprobación.
CD · Continuous Delivery

Paso 7 · Despliegue en stage con GitOps

  • GitOps: Argo CD o Flux leen el estado deseado desde Git (modelo pull)
  • Empaquetado: Helm o Kustomize
  • Admission control: Kyverno / OPA Gatekeeper rechazan lo que no cumple
  • Secretos: HashiCorp Vault, AWS Secrets Manager, Azure Key Vault + External Secrets
Guion: El pipeline no entra al clúster: solo cambia la versión en el repositorio de configuración. Argo CD ve el cambio y sincroniza. Así el pipeline no necesita credenciales del clúster, todo queda auditado en Git, y el rollback es un revert. Los secretos nunca están en Git: External Secrets los trae desde Vault o desde el gestor de secretos de la nube.
CD · Continuous Delivery

Paso 8 · Pruebas en stage

  • Smoke tests justo después del deploy
  • Integración y contratos: Pact, Postman/Newman
  • End-to-end: Cypress, Playwright, Selenium
  • DAST (Dynamic Application Security Testing): OWASP ZAP, Burp Suite
  • Carga: k6, JMeter, Gatling
Guion: Con la aplicación corriendo en stage se prueba como lo haría un usuario. Primero smoke tests, después integración y end-to-end. En paralelo, el DAST, por ejemplo OWASP ZAP, ataca la aplicación viva buscando vulnerabilidades que el análisis estático no ve. Y las pruebas de carga confirman que la versión aguanta el tráfico. Todo eso, más unos días de métricas sanas, es la evidencia para pasar a producción.
CD · Continuous Delivery

Pasos 9 y 10 · Gate, aprobación y producción progresiva

  • Ambientes protegidos: Azure DevOps environments, GitLab protected environments, GitHub environments
  • Gestión de cambios (ITIL, CAB) con la evidencia de stage
  • Estrategias: rolling, blue/green, canary + feature flags
  • Argo Rollouts / Flagger: canary con análisis automático y rollback automático
Guion: El gate es el punto de control entre stage y producción. En una telco como Claro normalmente hay un proceso de gestión de cambios, así que la aprobación lleva adjunta la evidencia de stage. Después la versión no llega de golpe: con canary empieza con el cinco por ciento del tráfico, Argo Rollouts compara errores y latencia contra la versión anterior, y si se degrada, hace rollback solo.
CD · Continuous Delivery

Paso 11 · Observar y cerrar el ciclo

  • Métricas y dashboards: Prometheus, Grafana, Datadog
  • SLO (Service Level Objective) y alertas al on-call
  • Métricas DORA: frecuencia de despliegue, lead time, tasa de fallo de cambios, MTTR (Mean Time To Recovery)
  • Postmortems sin culpables → mejoras al pipeline
Guion: El pipeline no termina en el deploy. La observabilidad confirma que la versión está sana, y las métricas DORA miden al propio proceso de entrega: qué tan seguido desplegamos, cuánto tarda un cambio en llegar, cuántos cambios fallan y qué tan rápido nos recuperamos. Eso es lo que le mostraría a Claro para demostrar que el proceso mejora.
Cloud security

Cloud security por capas

  • CSPM (Cloud Security Posture Management): Microsoft Defender for Cloud, AWS Security Hub, Prisma Cloud, Wiz
  • CWPP (Cloud Workload Protection Platform) / runtime: Falco, Amazon GuardDuty, Defender for Containers
  • CNAPP (Cloud-Native Application Protection Platform) = CSPM + CWPP + escaneos del pipeline en una sola plataforma
  • Benchmarks: CIS Benchmarks, kube-bench; auditoría: CloudTrail, Azure Activity Log
Guion: El pipeline protege lo que se despliega, pero la nube también hay que vigilarla en ejecución. El CSPM revisa la configuración de la cuenta contra los CIS Benchmarks, por ejemplo buckets públicos o llaves sin rotar. El CWPP vigila las cargas corriendo, por ejemplo Falco detecta si alguien abre una shell dentro de un contenedor. Las plataformas CNAPP, como Wiz o Prisma Cloud, juntan todo.
Cloud security

Identidad del pipeline: sin llaves fijas

  • OIDC (OpenID Connect): el job pide un token y la nube lo cambia por una credencial temporal
  • AWS: rol IAM con trust policy por repo y rama · Azure: workload identity federation
  • Mínimo privilegio: un rol por pipeline y por ambiente
  • Cifrado con KMS (Key Management Service), secretos en Vault o el gestor de la nube
Guion: El riesgo más grande de un pipeline es una llave de la nube guardada como variable: si se filtra, sirve para siempre. Con OIDC el pipeline no guarda llaves: en cada ejecución pide un token, la nube valida de qué repositorio, rama y ambiente viene, y entrega una credencial que vence en minutos con el rol mínimo. En MercadoLibre hacía hardening justamente en IAM, cifrado y segmentación de red.
Resumen

Resumen: paso → herramienta

  • 1 PR: Git, Gitleaks, branch protection · 2 Build: Maven/npm, JUnit/pytest, JaCoCo
  • 3 Calidad: SonarQube quality gate · 4 Seguridad: Semgrep/Checkmarx, Snyk, Gitleaks, Syft
  • 5 Imagen: Docker, Trivy, Cosign, Artifactory/Harbor · 6 IaC: Terraform, Checkov, OPA
  • 7 Deploy: Argo CD, Helm, Vault, Kyverno · 8 Pruebas: Cypress, OWASP ZAP, k6
  • 9-10 Producción: ambientes protegidos, Argo Rollouts · 11 Observar: Prometheus, Grafana, DORA
  • Nube: Defender for Cloud / Security Hub, Falco, OIDC
Guion: Si me preguntan por un paso, digo el control y la herramienta: el quality gate es SonarQube, el SCA es Snyk o Dependency-Check, la imagen se escanea con Trivy y se firma con Cosign, la IaC se escanea con Checkov, el DAST es OWASP ZAP, el despliegue es GitOps con Argo CD.
